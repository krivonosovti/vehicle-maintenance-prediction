# Работа над проектом

1. Создайте Issue. После включения workflow заголовок автоматически получит префикс VMP-XX по номеру Issue: #4 → VMP-04. Issues и PR имеют общий счётчик, пропуски номеров нормальны.
2. Создайте ветку от актуальной master: feat/VMP-04 или feat/VMP-04-short-description.
3. Откройте PR в master с заголовком VMP-04: Название работы.
4. В описание добавьте отдельную строку Closes #4. GitHub свяжет PR с задачей и закроет её после слияния в основную ветку.
5. Дождитесь успешной проверки VMP PR policy; ревью коллег рекомендуется, но approval не является условием слияния. Устраните полученные замечания.
6. Используйте Squash and merge. Название итогового коммита по умолчанию берётся из заголовка PR; GitHub может дописать номер PR. Не заменяйте его вручную.

## Ревью команды

Логины двух участников пока неизвестны, поэтому автоматическое назначение отложено.
Когда все трое получат доступ, в Settings → Secrets and variables → Actions → Variables создайте переменную VMP_TEAM: три реальных GitHub-логина через запятую, включая krivonosovti.
Workflow запросит ревью у двух коллег, исключая автора. Это необязательное ревью, не блокирующее слияние. Секреты и персональные токены не нужны.
Отсутствие переменной явно отмечается в журнале; фиктивные логины не используются.

## Защита основной ветки

Настройка защиты должна применяться к master, а не к feat/VMP-*:
- Require a pull request before merging.
- Require approvals: выключено (0 обязательных одобрений).
- Require conversation resolution.
- Require status checks: VMP PR policy (выбрать после первого запуска).
- Do not allow bypassing the above settings.
- Force pushes и удаление ветки не разрешать.

На момент настройки GitHub показывает Not enforced для защиты этого приватного репозитория.
Пока тариф не поддерживает защиту, проверки сообщают об ошибках, но не запрещают merge или прямой push. Команда должна соблюдать правила вручную.
Приватность репозитория не менять ради обхода ограничения без отдельного решения владельца.

## Включение автоматизации

Файлы автоматизации вводятся отдельным PR. Префиксы Issues и запросы ревью начнут работать после его слияния в основную ветку.
Для существующих открытых Issues после слияния достаточно отредактировать заголовок/описание, чтобы применить префикс.
